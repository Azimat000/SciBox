## Правила, которые держат сервер масштабируемым

1. Сервер без состояния в памяти: сессии, лимиты, очереди, блокировки живут в PostgreSQL. Любой запрос может прийти в любую копию.
2. Фоновые задачи безопасны при нескольких копиях: строки берутся `FOR UPDATE SKIP LOCKED` или под рекомендательной блокировкой (advisory lock); повтор задачи не создаёт дублей.
3. Каждый список ограничен: пагинация с максимальным размером страницы; на больших таблицах листание по ключу, а не `OFFSET`.
4. У каждого запроса к базе и внешнему сервису есть срок (`context` с таймаутом, `statement_timeout`).
5. Горячие запросы проверены `EXPLAIN (ANALYZE, BUFFERS)` на объёме из таблицы выше; без последовательного чтения больших таблиц.
6. Файлы не проходят через память целиком и не лежат в базе (срез 23, D-157, D-159): приём потоком, в памяти одна часть записи (5 МиБ), выдача потоком из хранилища.
7. Справочники и числа главной кешируются на короткий срок.

## Как выкладывать индексы на больших таблицах

Миграции создают индексы обычным `CREATE INDEX IF NOT EXISTS …`: на пустой и маленькой базе это мгновенно. На базе с миллионами строк обычный `CREATE INDEX` блокирует запись в таблицу на минуты. Порядок для боевой выкладки (миграции 00020, 00021 и дальше):

1. Перед выкладкой новой версии вручную создать индексы из миграции командой `CREATE INDEX CONCURRENTLY IF NOT EXISTS <то же имя> ON …` (без блокировки записи; не в транзакции, поэтому не через goose).
2. Выложить версию: `IF NOT EXISTS` пропустит готовые индексы, миграция останется быстрой.
3. Столбцы и таблицы, которые миграция заполняет (`profile_search`, `profiles.q12_total`, `vacancy_search.codes`), на больших таблицах заполняются долго (80 с на 175 тысячах профилей): выкладывать в окно с малой нагрузкой.
4. После выкладки проверить `\di+` на недостающие и «битые» (`indisvalid = false`) индексы: прерванный `CONCURRENTLY` оставляет такой индекс, его надо удалить и создать заново.
