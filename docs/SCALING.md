# Масштабирование и производительность сервера

Живой документ серверной очереди (срезы 18–29, D-138). Здесь цели в цифрах, правила, которые держат сервер масштабируемым, и замеры по срезам. Срез, который что-то измерял, дописывает строку в «Замеры»; цифры без даты и условий не пишутся.

## Правила, которые держат сервер масштабируемым

1. Сервер без состояния в памяти: сессии, лимиты, очереди, блокировки живут в PostgreSQL. Любой запрос может прийти в любую копию.
2. Фоновые задачи безопасны при нескольких копиях: строки берутся `FOR UPDATE SKIP LOCKED` или под рекомендательной блокировкой (advisory lock); повтор задачи не создаёт дублей.
3. Каждый список ограничен: пагинация с максимальным размером страницы; на больших таблицах листание по ключу, а не `OFFSET`.
4. У каждого запроса к базе и внешнему сервису есть срок (`context` с таймаутом, `statement_timeout`).
5. Горячие запросы проверены `EXPLAIN (ANALYZE, BUFFERS)` на объёме из таблицы выше; без последовательного чтения больших таблиц.
6. Файлы не проходят через память целиком и не лежат в базе (срез 23, D-157, D-159): приём потоком, в памяти одна часть записи (5 МиБ), выдача потоком из хранилища.
7. Справочники и числа главной кешируются на короткий срок.
8. Фоновая работа вынесена в `worker` и общее расписание (срез 25): сколько бы ни было копий, задача кластера идёт в одном месте за срок; письма и файлы берутся в аренду; соединений с базой у воркера не больше 10.
9. Внешние сервисы за ограничителем и предохранителем (срез 25): одновременных обращений ограниченное число, после серии сбоев обращений нет.

## Нагрузочный тест (срез 27)

Запуск: `make load-test` (ступени 100…600 зап/с по 60 секунд; свои: `make load-test STEPS=100,300 DURATION=30s`), `make load-smoke` (одна короткая ступень). Нужны: `make load-data` (база `scibox_load`), `k6`, Docker. Скрипт `scripts/load-test` собирает сервер, готовит данные (`loadtest/fixtures.sql`: 4000 учёных и 300 владельцев организаций с живыми сеансами, пары «человек — вакансия» для откликов), поднимает две копии сервера (`:8091`, `:8092`) и воркер, гоняет `loadtest/scenario.js` ступенями и складывает в `loadtest/.run/<время>/` таблицы по запросам, профили процессора каждого процесса (`pprof` на внутреннем порту), снимки `/metrics` и журнал нагрузки машины. Результаты не входят в git.

**Как построена смесь.** Модель открытая: запросы приходят с заданной скоростью, как бы ни отвечал сервер, поэтому насыщение видно как «потеряно N запросов» и рост задержек. Копии чередуются по кругу. Каждый запрос несёт адрес из пула в 20 тысяч (`X-Forwarded-For`, `SCIBOX_TRUSTED_PROXIES=127.0.0.1`), поэтому настоящее ограничение частоты (запись в `rate_counters`) работает и входит в замер. Веса запросов (сумма 988, доля = вес / 988): гость — поиск вакансий 230 (без слов 50, по слову 100, по фильтрам 70, с опечаткой 10), страница вакансии 140, вакансии организации 20, главная 40, справочники 30, организации 30, каталог учёных 40, страница учёного 30; вошедший учёный — «кто я» 90, колокольчик 90, мои отклики 30, подбор 30, избранное и сроки 20, профиль 20, страница и состояние вакансии 50, поиск 20; сотрудник организации — отклики 30, мои вакансии 5, каталог 10; запись — вход 10, избранное 5, решение по отклику 5, отклик без файла 10, отклик с файлом 3. Бюджеты для проверки в сценарии: чтение p95 ≤ 200 мс, запись p95 ≤ 400 мс (отклик с файлом 1500 мс: файлы вне бюджета записи), p99 ≤ 1 с, 5xx < 0,1%, 429 и ошибок связи нет.

**Что нужно знать, читая цифры:**
1. Замер сделан на ноутбуке, где на одном процессоре работают k6, две копии сервера, воркер и виртуальная машина с базой (нагрузка машины 8–16, база больше памяти виртуальной машины). Сервер на настоящем платном сервере (D-138, пользователь 2026-10-10) будет отвечать быстрее; цифры ниже — нижняя граница, а не прогноз.
2. Узкое место везде одно: процессор базы. Go-сервер на 120 зап/с занимает 17% ядра на копию.
3. Антивирус при замере выключен (память): файлы откликов принимаются «на проверке».
4. `scibox_load` создаётся один раз (≈40 минут и 7 ГБ диска); после перезапуска Docker кеш холодный: первая ступень уходит на прогрев (60 зап/с, p95 1,8 с), поэтому перед настоящими ступенями прогонять `make load-smoke`.

**Что нужно сделать на настоящем сервере** (один раз после переезда, срез 28 и дальше): `make load-data SCALE=1` (или перенос копии базы), затем `make load-test`; сравнить с таблицей замеров выше; если цели из «Цели» не достигнуты, смотреть `loadtest/.run/<время>/` (`pg_stat_statements` включён в `docker-compose.yml`, для боевой базы включить так же), список «Известные узкие места» и профиль процессора.

## Как выкладывать индексы на больших таблицах

Миграции создают индексы обычным `CREATE INDEX IF NOT EXISTS …`: на пустой и маленькой базе это мгновенно. На базе с миллионами строк обычный `CREATE INDEX` блокирует запись в таблицу на минуты. Порядок для боевой выкладки (миграции 00020, 00021 и дальше):

1. Перед выкладкой новой версии вручную создать индексы из миграции командой `CREATE INDEX CONCURRENTLY IF NOT EXISTS <то же имя> ON …` (без блокировки записи; не в транзакции, поэтому не через goose).
2. Выложить версию: `IF NOT EXISTS` пропустит готовые индексы, миграция останется быстрой.
3. Столбцы и таблицы, которые миграция заполняет (`profile_search`, `profiles.q12_total`, `vacancy_search.codes`), на больших таблицах заполняются долго (80 с на 175 тысячах профилей): выкладывать в окно с малой нагрузкой.
4. После выкладки проверить `\di+` на недостающие и «битые» (`indisvalid = false`) индексы: прерванный `CONCURRENTLY` оставляет такой индекс, его надо удалить и создать заново.
