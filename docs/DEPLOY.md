# Выкладка на сервер (срез 28)

Как поднять ИОН на любом виртуальном сервере или в облаке с Docker и как им пользоваться дальше. Хостинг пока не выбран (D-138): всё ниже годится для любого российского провайдера. Для первой выкладки нужно примерно полдня и доступы, перечисленные в разделе 1.

Если код и этот документ расходятся, прав код (`deploy/`), а документ исправляется.

## 1. Что понадобится

| Что | Зачем | Заметки |
|---|---|---|
| Виртуальный сервер | всё работает на нём | минимум 4 ядра, 8 ГБ памяти, 80 ГБ диска SSD, Ubuntu 24.04 LTS или Debian 13; для цели «вся наука РФ» (`docs/SCALING.md`) 8 ядер и 32 ГБ |
| Домен | адрес сайта и сертификат | запись A (и AAAA) указывает на сервер; ждать обновления DNS до первого запуска |
| Хранилище файлов (S3) | CV, приложения, письма рекомендателей | Yandex Object Storage, Selectel, VK Cloud и т. п.; бакет **приватный**, шифрование на стороне провайдера включено (T-43) |
| Хранилище копий (S3) | копии базы и файлов | **другой бакет**, лучше у другого провайдера или в другом аккаунте: копия рядом с оригиналом не защищает от потери аккаунта |
| Почтовый сервис (SMTP) | письма со ссылками | порт 587 (STARTTLS) или 465 (TLS); у домена настроены SPF, DKIM, DMARC |
| Менеджер паролей или сейф | хранить пароли шифрования копий | см. раздел 6: без них копии не прочитать |

Сервисные аккаунты хранилищ создаются отдельно для файлов и для копий. Права: чтение, запись и удаление объектов только своего бакета, больше ничего.

## 2. Как всё устроено

Все части описаны в `deploy/docker-compose.prod.yml` и работают в Docker на одном сервере:

| Часть | Что делает | Наружу |
|---|---|---|
| `caddy` | принимает запросы на 80 и 443, сам получает и обновляет сертификат (Let's Encrypt, при отказе ZeroSSL), распределяет запросы между двумя копиями | 80, 443 |
| `app1`, `app2` | две копии сервера; если одна остановлена, вторая отвечает за обеих | нет |
| `worker` | фоновые задачи: письма, подбор, напоминания, проверка файлов, чистка | нет |
| `postgres` | база; непрерывно отправляет журнал изменений в хранилище копий | нет |
| `backup` | планировщик копий базы и файлов, метрики копий | нет |
| `clamav` | проверка файлов на вирусы | нет |
| `release` | одноразовый шаг выкладки: миграции и справочник журналов | нет |
| `prometheus`, `alertmanager`, `grafana`, `node-exporter` | мониторинг (профиль `monitoring`) | только 127.0.0.1 сервера |

Наружу из интернета открыты только порты 80 и 443. Секреты лежат файлами в `deploy/secrets/` (права 600). Образ сервера без оболочки, работает не от root, файловая система только для чтения.

## 3. Настройка сервера (чек-лист)

Выполняется один раз на чистом сервере, от пользователя с `sudo`.

- [ ] **Обновления.** `sudo apt update && sudo apt full-upgrade -y`, перезагрузка.
- [ ] **Пользователь.** Отдельный пользователь для работы (например, `scibox`), не `root`: `sudo adduser scibox && sudo usermod -aG sudo scibox`.
- [ ] **Вход по ключу.** Свой публичный ключ в `~scibox/.ssh/authorized_keys`; затем в `/etc/ssh/sshd_config.d/10-scibox.conf`: `PasswordAuthentication no`, `PermitRootLogin no`; `sudo systemctl reload ssh`. Не закрывайте текущую сессию, пока не проверили вход по ключу из другого окна.
- [ ] **Межсетевой экран.** Открыты только 22 (лучше ограничить своим адресом), 80, 443: `sudo ufw default deny incoming && sudo ufw allow 22/tcp && sudo ufw allow 80,443/tcp && sudo ufw allow 443/udp && sudo ufw enable`. Docker сам обходит `ufw` для опубликованных портов: поэтому compose публикует наружу только 80 и 443, а мониторинг привязан к `127.0.0.1`.
- [ ] **Автообновления безопасности.** `sudo apt install -y unattended-upgrades && sudo dpkg-reconfigure -plow unattended-upgrades`.
- [ ] **Точное время (NTP).** `timedatectl` должен показывать `System clock synchronized: yes` и `NTP service: active` (по умолчанию да). От часов зависят расписание задач и аренда писем: копия с часами, ушедшими больше чем на 2 минуты, перестанет исполнять задачи, и сработает тревога `JobsPausedByClock`.
- [ ] **Docker.** Установить Docker Engine и плагин compose по инструкции провайдера или docs.docker.com для вашей системы; `sudo usermod -aG docker scibox`; проверить `docker compose version` (нужна версия 2.30 и новее).
- [ ] **Ограничение журналов Docker.** Уже сделано в compose (`max-size 20m`, 5 файлов): журналы не заполнят диск.
- [ ] **Диск.** Не меньше 30% свободного места всегда; тревоги `DiskSpaceLow` (15%) и `DiskSpaceCritical` (5%) настроены.
- [ ] **Память базы.** `PG_SHARED_BUFFERS` в `deploy/.env` не меньше четверти памяти сервера, `PG_EFFECTIVE_CACHE_SIZE` около половины.
- [ ] **Перезагрузка сервера.** Все службы стоят с `restart: unless-stopped`: после перезагрузки поднимутся сами. Проверьте один раз: `sudo reboot`, затем `./deploy/compose ps`.

## 4. Если Docker Hub недоступен

Образы берутся с Docker Hub (`postgres`, `caddy`, `rclone`, `clamav`, `prom`, `grafana`, `node`, `golang`) и `gcr.io` (базовый образ сервера). Из России доступ к ним бывает нестабильным (на октябрь 2026 по сообщениям провайдеров Docker Hub отвечает с перебоями или отказом). Что делать, по порядку:

1. **Зеркало реестра в Docker.** В `/etc/docker/daemon.json` указать зеркала (проверьте актуальность адресов у своего провайдера, они меняются):
   ```json
   { "registry-mirrors": ["https://mirror.gcr.io", "https://dockerhub.timeweb.cloud"] }
   ```
   затем `sudo systemctl restart docker`.
2. **Свои адреса образов.** Все образы в compose заданы переменными, их можно перенаправить на зеркало или собственный реестр в `deploy/.env`: `CADDY_IMAGE`, `CLAMAV_IMAGE`, `PROMETHEUS_IMAGE`, `ALERTMANAGER_IMAGE`, `GRAFANA_IMAGE`, `NODE_EXPORTER_IMAGE`. Базовые образы сборки (`POSTGRES_IMAGE`, `RCLONE_IMAGE` в `deploy/postgres/Dockerfile`; `NODE_IMAGE`, `GO_IMAGE`, `RUNTIME_IMAGE` в `Dockerfile`) задаются через `--build-arg`, а для deploy.sh через `SCIBOX_DOCKER_BUILD_ARGS="--build-arg GO_IMAGE=... --build-arg NODE_IMAGE=..."`.
3. **Перенос готовых образов.** Со своего компьютера, где образы скачаны: `docker save имя:тег | gzip > file.tar.gz`, на сервере `gunzip -c file.tar.gz | docker load`. Образ самого сервера лучше собрать на компьютере и перенести так.

## 5. Первая выкладка по шагам

На сервере, под пользователем `scibox`:

```bash
git clone <адрес репозитория> scibox && cd scibox     # или скопируйте каталог проекта
cd deploy
./init-secrets.sh                      # создаёт случайные секреты и пишет, чего не хватает
cp env.example .env && nano .env       # домен, почта, адреса хранилищ, ресурсы
```

Файлы, которые выдают провайдеры, создаются руками без лишних пробелов и переводов строк:

```bash
printf '%s' 'ключ-доступа'    > secrets/s3_access_key
printf '%s' 'секретный-ключ'  > secrets/s3_secret_key
printf '%s' 'пароль-почты'    > secrets/smtp_password
printf '%s' 'ключ-доступа'    > secrets/backup_s3_access_key
printf '%s' 'секретный-ключ'  > secrets/backup_s3_secret_key
chmod 600 secrets/*
```

Проверка без запуска, затем выкладка:

```bash
./deploy.sh --check                    # все файлы на месте, compose настроен
./deploy.sh --build                    # собирает образ из этого каталога и выкладывает
```

Первый запуск занимает 10–20 минут: сборка, скачивание баз ClamAV (сотни мегабайт), получение сертификата. По окончании скрипт печатает «Готово» и адрес проверки. Проверьте в браузере `https://ваш-домен`.

Что проверить сразу после первого запуска:

1. `./compose ps` — все службы `healthy` или `running`.
2. `./compose logs --tail 50 app1` — нет строк уровня ERROR.
3. Регистрация на сайте → письмо пришло → вход работает.
4. Отклик с файлом PDF проходит; файл виден в бакете.
5. `./restore-check.sh` — **обязательно** (раздел 9): `ВОССТАНОВЛЕНИЕ ПРОВЕРЕНО`.
6. Тестовый вирус: файл `eicar.txt` с известной строкой теста EICAR, сохранённый как PDF-вложение отклика, должен быть отклонён (раздел 11).

## 6. Секреты и что хранить вне сервера

Файлы в `deploy/secrets/` (права 600, каталог 700, в git не попадают):

| Файл | Что это | Откуда |
|---|---|---|
| `db_admin_password`, `db_password`, `database_url` | пароли базы | создаёт `init-secrets.sh` |
| `ops_token` | секрет внутреннего порта (метрики) | создаёт `init-secrets.sh` |
| `grafana_admin_password` | вход в Grafana | создаёт `init-secrets.sh` |
| `s3_access_key`, `s3_secret_key` | хранилище файлов | провайдер |
| `smtp_password` | пароль почтового сервиса | провайдер |
| `backup_s3_access_key`, `backup_s3_secret_key` | хранилище копий | провайдер |
| **`backup_cipher_pass`** | **пароль шифрования копий базы** | создаёт `init-secrets.sh` |
| **`backup_files_crypt_pass`** | **пароль шифрования копий файлов** | создаёт `init-secrets.sh` |

**Два выделенных пароля сохраните отдельно от сервера** (менеджер паролей, сейф, печатная копия в надёжном месте). Копии шифруются на сервере до отправки, поэтому провайдер хранилища их прочитать не может. Но если сервер погибнет вместе с этими файлами, копии станут нечитаемыми навсегда. Проверка, что пароль сохранён верно: на любом другом компьютере `restore-check` (раздел 9) должен пройти с этими паролями.

Смена секрета: заменить файл, `./compose run --rm secrets-init`, затем `./compose up -d --force-recreate app1 app2 worker` (по одной копии, чтобы не было простоя). Смена `db_password` требует ещё `ALTER ROLE scibox PASSWORD '…'` в базе и нового `database_url`.

## 7. Обновление версии и откат

```bash
cd ~/scibox && git pull
deploy/deploy.sh --build               # новая версия без простоя
```

Что делает скрипт: собирает образ, раскладывает секреты, запускает шаг `release` (миграции и справочник), заменяет `app1`, ждёт готовности, заменяет `app2`, затем `worker`; Caddy тем временем отправляет запросы той копии, которая готова. Если любой шаг не прошёл, прежняя версия продолжает работать, а скрипт говорит, где остановился.

**Откат:** `deploy/deploy.sh --rollback` возвращает предыдущую версию (её имя записано в `deploy/.state/previous-image`). Миграции при откате не откатываются: они только добавляют (раздел 8), поэтому старая версия работает с новой схемой. Это проверено тестом `TestAnOlderServerAcceptsADatabaseMigratedFurther`.

Версию, которая сейчас работает: `docker inspect -f '{{.Config.Image}}' $(./deploy/compose ps -q app1)`.

## 8. Миграции базы без простоя

Правило «расширить, потом сжать» (D-186). Миграция в выпуске N только **добавляет** (таблица, столбец, индекс). Всё, что ломает прежнюю версию (удалить или переименовать столбец и таблицу, сменить тип, сделать столбец обязательным без значения, добавить ограничение), делается в отдельном выпуске после того, как ни одна копия предыдущей версии уже не нужна, и файл миграции помечается строкой `-- scibox:contract <причина>`. Тест `TestNewMigrationsOnlyExpandTheSchema` роняет `make test`, если новая миграция нарушает правило без метки.

- Индексы на больших таблицах: миграции создают их `CREATE INDEX IF NOT EXISTS`; перед выкладкой на большой базе создайте их заранее без блокировки записи (`docs/SCALING.md`, «Как выкладывать индексы»).
- Миграция ждёт блокировку не дольше 10 секунд (`lock_timeout`): лучше повторить выкладку, чем остановить сайт за долгим запросом.
- Команды, которые стирают данные (`migrate down`, `migrate reset`, `seed`), в боевом режиме отказывают без `SCIBOX_ALLOW_DESTRUCTIVE=on`.

## 9. Резервные копии, проверка и восстановление

Что делается само (контейнер `backup`, решения D-184, D-185):

| Что | Как | Как часто | Сколько хранится |
|---|---|---|---|
| База: журнал изменений | PostgreSQL отправляет в хранилище копий (pgBackRest, шифрование AES-256) | каждую минуту при записях (`archive_timeout=60`) | до 30 дней |
| База: полная копия | pgBackRest | раз в 7 дней | до 30 дней |
| База: разностная копия | pgBackRest | раз в сутки | до 30 дней |
| Файлы откликов | rclone, шифрование паролем `backup_files_crypt_pass` | раз в сутки | удалённые из хранилища файлы лежат в `deleted/<дата>` ещё 30 дней |

Потеря при аварии: минуты (журнал изменений). Срок 30 дней: так человек, удаливший аккаунт, исчезает и из копий не позднее чем через 30 дней (тот же срок, что требует 152-ФЗ при отзыве согласия, ст. 21; формулировку подтверждает юрист, T-40).

### Проверка (раз в месяц и после любой смены настроек копий)

```bash
deploy/restore-check.sh
```

Скрипт снимает «снимок» живой базы, отправляет журнал в архив, поднимает копию базы во временном каталоге на отдельном порту, сверяет версию схемы и число строк в ключевых таблицах с живой базой, проверяет целостность индексов (`pg_amcheck`) и наличие файлов, на которые ссылается база. Рабочая база и хранилище копий не меняются. Итог `ВОССТАНОВЛЕНИЕ ПРОВЕРЕНО` или строки `ОШИБКА`. Копия, которую ни разу не восстанавливали, копией не считается.

Что смотреть между проверками: тревоги `BackupDatabaseTooOld`, `BackupFilesTooOld`, `BackupFullTooOld`, `BackupAttemptFailed`, `WalArchiveFailing`, `BackupSchedulerSilent` (раздел 10) и `./compose exec backup scibox-entrypoint pgbackrest info` — список копий.

### Авария: сервер потерян, база нужна

Порядок на новом сервере (разделы 3 и 5, но без `./deploy.sh` до шага 4):

1. Подготовьте сервер, склонируйте проект, положите в `deploy/secrets/` **прежние** `backup_cipher_pass`, `backup_files_crypt_pass` и ключи хранилищ; заполните `deploy/.env` теми же значениями хранилищ.
2. Соберите образ базы: `docker build -t scibox-postgres:16.15 deploy/postgres`.
3. Восстановите каталог базы в пустой том (последняя копия и журнал до конца архива; для точки во времени добавьте `--type=time --target="2026-10-11 12:30:00+03"`):
   ```bash
   cd deploy
   ./compose run --rm --no-deps --entrypoint scibox-entrypoint backup \
       pgbackrest --stanza=main --delta restore
   ```
   Том `pgdata` должен быть пустым; сервис `backup` монтирует его только для чтения, поэтому для восстановления используйте временный запуск с записью: `docker run --rm -v scibox-prod_pgdata:/var/lib/postgresql/data --env-file … scibox-postgres:16.15 scibox-entrypoint pgbackrest …` (все переменные `PGBACKREST_*` те же, что в compose).
4. Поднимите базу: `./compose up -d postgres`; дождитесь `healthy`.
5. Файлы: из копии обратно в рабочий бакет: `rclone copy DST:current SRC:<бакет файлов>` с теми же переменными, что в `scibox-backup-lib` (проще всего из контейнера `backup`: `./compose run --rm --no-deps --entrypoint scibox-entrypoint backup sh -c '. scibox-backup-lib; files_rclone_env; rclone copy DST:current SRC:"$FILES_S3_BUCKET"'`).
6. `./deploy.sh <версия>` — запустить сервер на восстановленной базе.
7. **Повторить удаления (T-40).** Копии содержат людей, удалённых после момента, на который вы вернулись. Пока в проекте нет автоматического повтора, действуйте так: найдите в журнале Docker и в письмах поддержки просьбы об удалении аккаунтов за период между временем восстановления и аварией, и повторите их через экран «Настройки → Безопасность» (или сообщите людям). При восстановлении на «последний момент» (по умолчанию) этот период — минуты.
8. Сделайте `./restore-check.sh` и новую полную копию уже с нового сервера.

## 10. Мониторинг и тревоги

Prometheus, Alertmanager, Grafana и node-exporter поднимаются вместе с остальным (`MONITORING=off` в `.env` выключает). Они доступны **только с самого сервера** (`127.0.0.1`), в интернет не публикуются (T-52): заходить через туннель SSH с вашего компьютера:

```bash
ssh -L 3100:localhost:3100 -L 9190:localhost:9190 scibox@сервер
# затем в браузере: http://localhost:3100 (Grafana, вход admin и пароль из secrets/grafana_admin_password)
#                   http://localhost:9190 (Prometheus, страница тревог)
```

Тревоги (`monitoring/prometheus/rules/scibox.yml`, 37 правил) уходят письмом на `ALERT_EMAIL_TO` через ту же почту, что и сайт (T-53). Если почтовый сервис сам недоступен, тревога о нём придёт вместе с остальными, когда он вернётся, и видна в Prometheus; для независимой доставки добавьте второй получатель (Telegram-бот) в `deploy/render-alertmanager.sh` (раздел `receivers`).

Служебная тревога `Watchdog` горит всегда и никому не отправляется: если её нет на странице тревог Prometheus, не работает сама система тревог.

Журналы: `./compose logs -f app1`, строки JSON, в каждой номер запроса (`request_id`); этот же номер человек видит в заголовке ответа `X-Request-Id`. Журнал Caddy не содержит cookie и заголовков, адреса обрезаны до сети. Ошибки можно отправлять в свой GlitchTip: `SCIBOX_ERROR_DSN` в `.env`.

## 11. Проверки после переезда

| Что | Как | Закрывает |
|---|---|---|
| Антивирус | первый запуск скачивает базы; затем загрузить в отклик тестовый файл EICAR (см. https://www.eicar.org): должен быть отклонён сообщением «Антивирус нашёл в файле вирус»; `./compose exec clamav clamdscan --version` показывает свежие базы | T-41 |
| Хранилище файлов | бакет приватный (публичный доступ выключен), шифрование на стороне провайдера включено, ключ сервисного аккаунта ограничен этим бакетом | T-43 |
| Пул соединений | в схеме нет PgBouncer, поэтому параметры соединения (`statement_timeout`, `plan_cache_mode`, `random_page_cost`) работают; если добавите пул, задайте их на роли: `ALTER ROLE scibox SET statement_timeout = '10s'` и т. д. | T-46 |
| `ALTER DATABASE … SET pg_trgm…` (миграция 00021) | в схеме роль приложения владеет своей базой, поэтому команда проходит; на управляемой базе провайдера проверьте и при отказе задайте порог в параметрах роли | T-47 |
| Нагрузка | `make load-data SCALE=1`, затем `make load-test` на этом сервере (`docs/SCALING.md`, «Нагрузочный тест»); включить `pg_stat_statements` (уже включён) | цель 500 запросов в секунду |
| Настоящий адрес посетителя | в `./compose logs app1` у записи с `request_id` адрес сети посетителя, а не адрес Caddy | T-31 |

## 12. Если что-то не так

| Симптом | Что смотреть |
|---|---|
| Сайт не открывается | `./compose ps`; `./compose logs caddy` (сертификат: DNS указывает на сервер? порты 80 и 443 открыты?) |
| «502» от Caddy | `./compose logs app1 app2`; готовность: `./compose exec app1 /app/scibox healthcheck` |
| Выкладка встала на `release` | `./compose logs release`; чаще всего миграция ждёт блокировку (повторить) или нет доступа к базе |
| Письма не приходят | `./compose logs worker`; тревоги `MailQueueStale`, `MailQueueVeryStale`; проверьте `SMTP_*` и `smtp_password` |
| Файл «на проверке» долго | `./compose logs clamav`: базы ещё скачиваются или не хватает памяти (нужно 2–3 ГБ) |
| `WalArchiveFailing` | хранилище копий недоступно или ключи просрочены; журнал копится на диске: срочно починить (`./compose logs postgres backup`) |
| Заполняется диск | `docker system df`; журнал изменений базы копится при недоступном хранилище копий; старые образы: `docker image prune -a` |
| Сервер не принимает `X-Forwarded-For` | `SCIBOX_TRUSTED_PROXIES` (`TRUSTED_PROXIES` в `.env`) должен содержать адрес Caddy (`CADDY_IP`) |

## 13. Репетиция на компьютере разработчика

Вся боевая конфигурация поднимается на Mac с самоподписанным сертификатом, тестовыми секретами и локальными хранилищами (SeaweedFS, Mailpit, облегчённый ClamAV): `make prod-up` (адрес `https://localhost:8443`, письма `http://localhost:8026`), `make prod-e2e` (сквозные сценарии против неё), `make prod-restore-check`, `make prod-down`. Это та же `docker-compose.prod.yml` с наложением `docker-compose.local.yml`; настоящие секреты репетиция не использует.

Если папка проекта лежит в iCloud Drive (Документы), Mac выгружает файлы из памяти компьютера и контейнеры читают их с ошибкой «Resource deadlock avoided»: `deploy/local/prepare.sh` возвращает такие файлы автоматически, но сборка может идти долго. На сервере этого нет.
