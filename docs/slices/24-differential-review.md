# Срез 24: разбор своих правок (differential-review)

Дата 2026-10-10. Что смотрели: всё, что срез изменил в критичных зонах и рядом с ними: `profiles` (каталог учёных, триггеры текста и счётчика), `vacancies` (поиск), `matching` (подбор), `journals` (пересчёт счётчика), `dbpool` и `config` (пул и сроки), `apierr` (ответ 503), `httpcache`, `landing`, `refdata`, миграции 00020 и 00021. Базовая версия: коммит `9819c3b` (конец среза 23). Размер: средний (около 60 файлов), стратегия «по критичным путям».

## Что проверяли и вывод

| Вопрос | Вывод |
|---|---|
| Видит ли каталог то, что раньше не видел? Новая таблица `profile_search` хранит текст всех профилей, в том числе скрытых | Нет. Таблицу читает только запрос каталога, и режим приватности (`p.visibility = ANY(@modes)`), непустая должность и исключение самого смотрящего применяются до подсчёта числа найденных и до страницы; `total` и `capped` считают только видимых. Таблица стирается вместе с профилем (`ON DELETE CASCADE`); `TestErasedPersonLeavesNothingToRecogniseThemBy` просматривает и её (прошёл), карта ПДн дополнена (`TestPersonalDataMapCoversEveryTable`). Таблицы кто-либо ещё не читает: `profile_search` нет ни в одном другом запросе, кроме каталога |
| Остаётся ли в тексте поиска чужое: удалён аккаунт, скрыт профиль, закрыта вакансия | Тексты пересобирают триггеры при любом пути записи (профиль, специальности, имя в аккаунте; статус вакансии и дата публикации): `TestProfileSearchFollowsTheProfile`, `TestSearchRowFollowsTheStatus`. Закрытая вакансия не находится ни по словам, ни по области (`TestSearchCodesFollowTheSpecialties`) |
| Не пропало ли что-то из прав и приватности из-за переписанных запросов | Запросы переписаны целиком (`found` → `page` → карточки), условия видимости перенесены без изменений; таблицы «кто что видит» (`TestCatalogWhoSeesWhat`, `TestCatalogNeverShowsHidden`, `TestAccessTable` на 103 адресах) прошли без правок |
| Утечка значений в журнал медленных запросов | В журнал идут имя запроса, время, число строк. Текст запроса и параметры не пишутся (`TestSlowQueriesAreLogged` кладёт почту в параметр и проверяет, что её нет); у запроса без имени пишется начало текста, но запросы проекта параметризованы и значений в тексте не содержат |
| Ошибка базы по сроку раскрывает ли подробности | Нет: ответ 503 с фиксированным текстом и `Retry-After`, подробности только в журнале (`TestWriteInternalDatabaseTimeout`); обрыв самим человеком по-прежнему 499 без шума |
| Общий кеш: попадает ли в него личное | В кеше только числа главной и справочники (одинаковы для всех); данных человека и сеанса там нет, `Cache-Control: public` стоит только на них, остальной `/api` по-прежнему `no-store` (`TestSecurityHeaders`, `TestPerimeter` прошли) |
| Инъекции | Новых динамических запросов нет; `ALTER DATABASE … SET` в миграции строится через `format('%I', current_database())` |
| Сбой базы не превращается в «пусто» | Новые пути (поиск, каталог, пересчёт счётчика, кеш) возвращают ошибку; ошибка кеша не сохраняется (`TestCacheDoesNotKeepFailures`); `TestDatabaseFailuresAreNeverSwallowed` в `profiles`, `vacancies`, `matching`, `journals` прошли |

## Находки

| № | Что | Решение |
|---|---|---|
| 1 | Подбор слов (`hits`) берёт самые свежие совпадения до проверки приватности. Если у слова много совпадений и часть профилей скрыта, скрытые занимают места в окне из тысячи, и человек видит меньше, чем есть видимых | Записано (D-161): окно — приближение для частых слов; на безопасность не влияет (скрытое не показывается), на полноту выдачи для частого слова влияет. Точная переработка (приватность внутри окна) потребует `visibility` в `profile_search`: сделать, если нагрузочный тест (срез 27) или жалобы покажут проблему |
| 2 | `plan_cache_mode = force_custom_plan` заставляет планировать каждый запрос заново: у тяжёлых поисковых запросов 5–10 мс планирования. При 150 поисках в секунду это около 0,75 ядра | Принято (D-164): без него общие планы теряют индексы и запросы идут в сотни раз дольше; расход замерить под нагрузкой (срез 27) |
| 3 | Параметры запуска соединения не работают через PgBouncer в режиме transaction | Записано: T-46 (срез 28) |
| 4 | Миграция 00021 выполняет `ALTER DATABASE … SET`; на управляемом хостинге права может не быть, тогда порог поиска с опечатками остаётся 0,6 | Записано: T-47 (срез 28) |
| 5 | Первая версия генератора нагрузочных данных брала слова из словаря в 80 слов и давала заведомо неверные замеры (каждое слово находилось в каждом тексте) | Исправлено до замеров (D-166); итоговые цифры сняты на данных с неравномерной частотой слов |
| 6 | Во время работы выяснилось, что папка проекта лежит в синхронизируемых с iCloud «Документах», и при заполнении диска macOS выгрузила в облако часть файлов, в том числе служебный файл git и 1700 файлов `node_modules`, которые не скачивались обратно («Operation timed out») | Исходники и история не пострадали (проверено сверкой с коммитом); файлы `node_modules` скачаны чтением, `.git/index` в этой сессии обходился временным индексом. Записано в HANDOFF: не держать проект и базы на диске с малым запасом, рассмотреть вывод проекта из синхронизации |

## Ограничения разбора

Разбор сделан по коду, тестам и замерам, без внешнего сканера (semgrep) и без фаззинга: это срез 29. Параллельность новых путей проверена тестами с `-race`; работа двух копий сервера с общим кешем не требуется (кеш у каждой копии свой, ответы публичные). Нагрузочная цифра снята на половине объёма и одной копии сервера.
