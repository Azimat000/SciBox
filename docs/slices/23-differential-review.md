# Срез 23: разбор своих правок (differential-review)

Дата 2026-10-09. Что смотрели: всё, что срез добавил или изменил в критичных зонах: `files` (склад, чтение запроса, выдача), `blobstore`, `antivirus`, `filework`, `applications` (отклик, выдача файла), `references` (письмо по ссылке), `dataexport`, `erasure`, `config`. Базовая версия: коммит `7262262` (конец среза 22). Размер: средний (около 80 файлов), стратегия «по критичным путям».

## Что проверяли и вывод

| Вопрос | Вывод |
|---|---|
| Можно ли получить чужой файл или чужой ключ объекта? | Нет. Ключи создаёт только сервер (`files/<uuid>`), берутся из строки базы по паре «номер файла + номер отклика», права проверяются тем же кодом, что и раньше (`readerOf`, `Kind.VisibleTo`); `TestAccessTable` (103 адреса) и таблицы «кто → какой файл» прошли без правок прав |
| Может ли организация получить непроверенный или заражённый файл? | Нет: выдача требует `clean` (`File`), список для организации прячет `infected`, `pending` виден как «проверяется»; письма рекомендателей так же (`ListForStaff`) |
| Можно ли через сбой антивируса или хранилища пропустить файл или потерять отклик? | Нет: любой сбой это `ErrUnavailable` (не вердикт) → `pending`; сбой хранилища при записи → 503, отклик не создаётся; пропавший объект проверенного файла → 500, а не «нет файла» |
| Усиление нагрузки анонимом | Закрыто в срезе: часть `data` идёт первой, мёртвая ссылка рекомендателя и неверные поля отвергаются до приёма файла; ссылка рекомендателя дополнительно ограничена 30 запросами в минуту |
| Потеря файла из-за удаления «лишнего» | Объекты удаляются сразу только после **известного** отказа до записи в базу; при сбое базы (в том числе при фиксации) они остаются, чистка осиротевших берёт только объекты старше суток без строки и отказывается работать при массе «сирот» |
| Стирание аккаунта | Объекты ставятся в очередь удаления в той же транзакции, строки стираются, ключ вычёркивается после удаления объекта (`TestEraseRemovesPersonalData`, сквозной тест на настоящем хранилище) |
| Журнал, имена, секреты | Название вируса, ключи и имена файлов других людей в ответы не попадают; ключи хранилища в сообщениях настроек не печатаются (`TestProductionRefusesUnsafeSettings`) |

## Находки

| № | Что | Решение |
|---|---|---|
| 1 | Человек, оборвавший загрузку посреди проверки, включал 30-секундную паузу антивируса для всех (отмена запроса давала `ErrUnavailable`), то есть любой мог держать чужие файлы «на проверке» | Исправлено: пауза включается, только если сам запрос ещё жив (`TestAClientThatLeavesDoesNotSwitchTheChecksOff`) |
| 2 | Обрыв загрузки человеком выглядел как поломка хранилища (503 и запись об ошибке) | Исправлено: возвращается ошибка отмены, ответ 499/без шума (`TestAClientThatLeavesDuringTheUploadIsNotAStorageFailure`) |
| 3 | Первая версия облегчённого ClamAV знала только хеш точного файла EICAR и пропускала EICAR внутри PDF (замечено в сквозном тесте на настоящем ClamAV, не в подставном) | Исправлено: подпись по телу (`eicar.ndb`), тест «EICAR внутри PDF» на настоящем ClamAV (`TestRealClamAV`) |
| 4 | Локальный ClamAV облегчённый: боевую настройку проверить не на чем | Записано: T-41, срез 28 |
| 5 | Файл выдаётся через наш сервер, а не подписанной ссылкой: сеть сервера станет узким местом при большой нагрузке | Записано в `docs/SCALING.md` (срез 27) |

## Ограничения разбора

Разбор сделан по коду и тестам, без внешнего сканера (semgrep) и без фаззинга разборщика multipart: это срез 29. Параллельность проверена тестами с `-race` и четырьмя копиями задачи; на двух настоящих процессах сервера не проверялось (срез 25).
