# Срез 26: разбор своих правок по `differential-review`

Дата 2026-10-10. Что менялось в критичных зонах: `config` (настройки внутреннего порта, журнала, адреса GlitchTip), `jobs` (наблюдатель, `ClockSkewed`), `dbpool` (наблюдатель), новые `opsserver` и `errreport`; в остальном: `httpapi` (порядок промежуточных обработчиков, журнал запроса, перехват паники), `apierr` (записи с контекстом), `cli` (сборка журнала и процессов). Метод: чтение разницы с вопросом «что это даёт нападающему и что это может сломать» (blast radius: `WriteInternal` вызывается из десятков обработчиков, `newLogger` из каждой команды).

## Находки

| № | Что | Судьба |
|---|---|---|
| 1 | `errreport.Close` ждал доставки всей очереди: при недоступном GlitchTip сто отчётов по пять секунд задержали бы остановку процесса почти на восемь минут (сбой «чужой» системы блокирует нашу мягкую остановку) | исправлено: `CloseWait` 5 секунд, затем отмена; тест `TestCloseDoesNotHangOnAnUnreachableTracker` |
| 2 | Ответы промежуточных обработчиков (проверка входа, 429, ошибка базы при проверке сеанса) считались как `api_unknown`: метрика по адресам теряла самые интересные ответы | исправлено: поиск шаблона у роутера (`RouteNamer.Finder`), тест `TestResponsesWrittenBeforeRoutingAreCountedByTheirRoute`, проверено на живом стенде (429 у `/api/auth/login`) |
| 3 | Поле журнала `token` (булево «защищён ли порт») маскировалось целиком по правилу `sensitiveKey` | исправлено: поле `protected`; правило маски не менялось |
| 4 | `/readyz` без секрета выполняет проверку базы на каждый запрос: теоретическое усиление нагрузки для того, кто достучался до внутреннего порта | принято: порт не публичный (петля или частная сеть, проверка в бою), оркестратор опрашивает раз в несколько секунд; ответ без деталей |
| 5 | `internalHost` считает внутренним имя без точки (служба в сети compose); при неудачном поисковом домене имя могло бы разрешиться наружу | принято: секрет задаётся и в этом случае (рекомендовано в docs/DEPLOY.md, срез 28); имя с точкой внутренним не считается |
| 6 | В отчёт об ошибке уходит поле `path` целиком | проверено: параметры путей API — номера (uuid), `slug` организации (публичный) и `token` (длинная случайная строка маскируется `logmask`); почт и имён в путях нет. Новый маршрут с именем человека в пути нарушил бы это: правило записано в `docs/SECURITY.md` (T-51) |
| 7 | Запрос с 5xx в журнале стал предупреждением, раньше был Info | сознательно: ошибка уже записана уровнем Error там, где случилась; запись запроса не должна дублировать её в GlitchTip |
| 8 | Новый обработчик журнала в цепочке: сбой отправителя не должен ронять запись | проверено: `Handler.Handle` не возвращает ошибок отправителя, очередь неблокирующая, сбой доставки пишется в журнал без отправки отчётов (`SetLogger`), чтобы не зациклиться |

## Что не нашлось
- Ничто из нового не доступно на публичном порту (тест обходит `/metrics`, `/livez`, `/readyz`, `/debug/pprof/…`).
- Метки метрик не содержат пути, номеров объектов, почт (тест на 2000 разных запросов даёт 4 ряда).
- Маска журнала по-прежнему стоит первой: ни журнал, ни GlitchTip не видят немаскированного (`TestEveryLoggerGoesThroughTheMask`, `TestNoLoggerBypassesTheMask` зелёные).
