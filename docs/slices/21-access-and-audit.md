# Срез 21. Права доступа на каждом адресе и журнал действий

Начат 2026-10-08. Серверная очередь (D-138). Угрозы T-15, T-16, T-17 и T-34 из `docs/SECURITY.md`.

## Цель

Для каждого адреса API записано, кому что отвечает сервер, и тест это проверяет; на чужие закрытые объекты сервер отвечает так же, как на несуществующие; важные действия остаются в журнале, который пишется в одной транзакции с самим действием, и владелец организации видит журнал своей организации.

## Что уже было до среза (проверено по коду)

- Права внутри организации решает `internal/access`, в сервисах стоят таблицы `TestWhoCanDoWhat` по каждой операции. Нет проверки на уровне HTTP: «все адреса роутера × все виды людей».
- Отклики, файлы, приглашения на вакансии: чужому всегда 404. Вакансия: опубликованная и закрытая публичны (403 не раскрывает ничего), черновик и архив для чужого 404 (D-055). Организации и подразделения публичны (403 допустим).
- Журнала действий нет. `rate_events` и `notifications` журналом не являются.

## Задачи

### Сервер
1. Таблица доступа (T-15, T-16): тест `internal/cli` `TestAccessTable` обходит все адреса настоящего роутера (`chi.Walk`), требует для каждого строку в таблице и проверяет «адрес × вид человека → ответ». Для закрытых объектов сверяет, что ответ чужому совпадает с ответом на несуществующий номер.
2. Исправить найденные утечки 403 вместо 404 (уже найдено: приём приглашения по номеру отвечает 403 `invitation_wrong_email` чужому, а несуществующему 400).
3. Журнал (T-17): миграция `00017_audit_log.sql` (таблица только для дописывания, защита триггером), пакет `internal/audit` (критичная зона 97%): события, запись в транзакции действия, адрес человека из контекста запроса, чтение для владельца.
4. Записи журнала в тех же транзакциях: смена роли и уход сотрудника, приглашения сотрудников (отправка, отзыв, приём), назначение руководителя подразделения, смена статуса вакансии (публикация, закрытие, архив, повторное открытие), решения по откликам и приглашения кандидатам, первое открытие отклика сотрудником, выдача файла отклика сотруднику, приглашения учёных на вакансии и их отзыв, вход, смена и сброс пароля, смена и откат почты, просьба об удалении аккаунта и её отмена.
5. `GET /api/organizations/{slug}/audit?before=&limit=` — только владелец; листание по номеру записи, без `OFFSET`.
6. Стирание аккаунта (`erasure`): адрес в журнале стёртого человека очищается (единственное разрешённое изменение записей журнала).
7. T-34: приём приглашения и стирание аккаунта сериализуются блокировкой строки организации; организация не остаётся с сотрудниками без владельца.

### Интерфейс
- Вкладка «Журнал» в управлении организацией (`/my-organization/:slug/audit`), только владельцу: простой список «кто, что, над чем, когда», «Показать ещё», состояния: загрузка, ошибка, пусто, длинные данные.

### Данные
- Демо-организациям добавить записи журнала, чтобы экран не был пустым.

## Что проверяем

- `TestAccessTable`: 100% адресов роутера есть в таблице, нет лишних строк; каждая клетка «адрес × вид человека» совпадает с ожидаемой.
- Журнал: запись и действие откатываются вместе; нельзя изменить и удалить запись; чужая организация журнал не видит; ПДн в записях только минимум (D-147…).
- Пороги: `audit` ≥ 97%, затронутые критичные зоны не ниже прежнего.

## Готово, когда (из ROADMAP)

- [ ] таблица покрывает 100% маршрутов;
- [ ] T-15, T-16, T-17 закрыты (и T-34);
- [ ] журнал пишется в одной транзакции с действием;
- [ ] `make test` зелёный, `make lint-new` = 0, `make vulncheck` без новых находок, `differential-review` по правкам критичных зон.

## Риски

- Журнал сам содержит ПДн (кто что делал, адрес): минимум полей, права, очистка адреса при стирании аккаунта, срок хранения — срез 22.
- Запись журнала в транзакции действия: сбой записи отменяет действие (для выдачи файла — отказывает в выдаче). Это сознательно (закрыто «по умолчанию»).
