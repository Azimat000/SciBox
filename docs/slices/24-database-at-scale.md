## Сделано

### Данные и замеры
- Генератор на SQL (`generate.sql`): всё по таблице `docs/SCALING.md` с масштабом (1 = полный объём, ≈ 12 ГБ), словарь в 2500 слов с неравномерной частотой, настоящие журналы SCImago, детерминированные идентификаторы, триггеры и внешние ключи на время загрузки выключены, текст поиска собирается в конце. Загрузка масштаба 0,5 занимает около 40 минут.
- Замерщик `TestHotQueriesOnLoadData` (`make load-check`): 43 запроса через настоящий роутер и пул; прогрев; бюджеты по запросам; отчёт в Markdown (`SCIBOX_LOAD_REPORT`).

### Что нашли замеры и как исправлено
| Было | Причина | Исправление |
|---|---|---|
| Каталог 44–65 секунд | текст профиля собирался на лету для каждого профиля, счётчик Q1–Q2 подзапросом на каждый, подсчёт всего каталога | `profile_search` с индексами, `q12_total`, `h_max`, предел выдачи, карточка только для страницы |
| Поиск вакансий по слову 2–4 секунды | индекс по тексту всех вакансий за годы (85% архив) и план, обходивший все открытые | отметка `open`, индексы только по открытым, выбор подходящих по индексу до остальных условий (`hits`), самые свежие совпадения |
| Первая страница поиска 80 мс | соединение с `vacancy_search` и сортировка 13 тысяч строк | `LEFT JOIN`, который планировщик убирает без слов; индекс порядка `(published_at DESC, id)`; `random_page_cost = 1,1` |
| Фильтр «область науки» 1 секунда | `LIKE` по неиндексируемому выражению, чтение тысяч строк архива | `codes` с кодами групп и областей, пересечение массивов по индексу |
| Поиск с опечатками 120–340 мс | сходство слов считалось по всем строкам, порог 0,35 находил треть профилей | триграммный индекс, порог 0,5 (D-163) |
| Подборка «Подходящие вам» 100 мс | разбор кодов специальностей на лету | `vacancy_search.codes` |
| Универсальные запросы с общим планом | после пяти выполнений PostgreSQL запоминает план без значений параметров и теряет индексы | `plan_cache_mode = force_custom_plan` в пуле |
