# Срез 4: организации и подразделения

Статус: готов. 2026-10-03.

## Цель
Любой вошедший человек может создать организацию, добавить подразделения, пригласить сотрудников по почте с ролями (владелец, кадровик, руководитель подразделения). У организации и подразделения есть публичные страницы; есть каталог организаций. Вакансий ещё нет (срез 5), поэтому в списках вакансий пустое состояние.

## Решения (дописаны в DECISIONS, D-045…D-052)
- Права вынесены в чистый пакет `internal/access`, без базы: `Actor.Can(...)`. Сервис организаций ничего не решает сам, только спрашивает `access`.
- Адрес организации по названию (`/organizations/ugatu-materials`), адрес подразделения по id.
- Приглашение по почте: одноразовая ссылка на 7 дней, принять может только аккаунт с той же почтой.
- Один руководитель на подразделение (`units.head_user_id`).

## Задачи

### Сервер
1. Миграция `00003_organizations.sql`: `organizations`, `org_members`, `units`, `org_invitations`.
2. SQL-запросы sqlc: `organizations.sql`, `units.sql`, `members.sql`, `invitations.sql`.
3. `internal/access` (критичная зона): роли, разрешения, табличные тесты на каждую пару «роль → действие».
4. `internal/orgs` (критичная зона): сервис (создать / изменить организацию, подразделения, руководитель, сотрудники, приглашения, принять приглашение), каталог и публичные страницы, письма, HTTP-обработчики, тесты вместе с кодом, сбои базы по очереди.
5. `apierr.DecodeJSON` для общего чтения JSON.
6. Подключение в `httpapi.NewRouter` и `cli`.
7. Демо-данные: `server/seed/` (вымышленные организации и люди, реальные города), команда `make seed`.

### Интерфейс
1. Каталог `/organizations` (поиск, тип, пустое состояние, загрузка, ошибка).
2. Публичная страница организации и подразделения.
3. `/my-organization`: мои организации, приглашения для меня, создание.
4. Управление организацией: данные, подразделения, сотрудники и приглашения.
5. Страница принятия приглашения `/invitations/accept?token=`.
6. Все тексты в `ru.ts`; состояния: пусто, загрузка, ошибка, длинные данные, нет прав.

## Что проверяем
Полный путь в браузере: регистрация → создание организации → подразделение → приглашение (письмо в Mailpit) → принятие вторым аккаунтом → видимость по ролям → публичные страницы. `make test` зелёный с порогами.

## Риски
- Объём большой: следим, чтобы права были в одном месте (`access`).
- Имя руководителя на публичной странице подразделения: показываем только отображаемое имя, не почту.
- Удаление организации и вакансий-зависимостей откладываем: удаление организации «по обращению», как удаление аккаунта.

## Отступления от плана
- Формы подразделений сделаны страницами, а не окнами (окно только для подтверждений: удалить, убрать, выйти). Причина: окно для формы не нужно, а у страницы есть ссылка.
- Добавлены вещи сверх списка среза: каталог организаций, список «Мои приглашения» (принятие без ссылки), ограничение «5 организаций в сутки», уход из организации.
- Удаление организации не делали (D-051).
- Из-за разрастания `orgs` добавлен в критичные зоны (97%), хотя в плане был только `access`.

## Проверки
- `make test`: зелёный. Тесты сервера с настоящей базой, сбои базы по очереди, гонки (последний владелец, одна ссылка приглашения), таблица «роль × действие».
- Один раунд во встроенном браузере: компьютер и телефон (375). Найдено и исправлено: отступы и ширина колонки роли в списке сотрудников, не хватало стрелки у списка ролей, отступ у заголовка формы подразделения.
- `break-ui` на предельных данных (организация с названием 190 знаков, 10 тем по 80 знаков, сайт 250 знаков, 120-знаковое имя и длинная почта у сотрудника): горизонтальной прокрутки нет; исправлено: мельче заголовок для длинных названий, показ сайта только доменом, короткий заголовок пустого состояния вакансий, ссылки в списке подразделений без подчёркивания.
- `/impeccable audit` кодом: детектор приёмов без замечаний; цели касания: мелкие кнопки на телефоне увеличены до 44px; тёмной темы нет (по дизайну).
- Письмо-приглашение проверено в Mailpit (текст, ссылка, принятие в браузере от начала до конца).
- Не делалось: `/impeccable critique` отдельным проходом и `web-design-guidelines` (долг, см. HANDOFF).
